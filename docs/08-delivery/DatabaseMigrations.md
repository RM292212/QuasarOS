# DatabaseMigrations.md

## Purpose

Define safe evolution of the PostgreSQL/PostGIS schema without corrupting scientific metadata or causing avoidable downtime.

## Tooling

Alembic is the schema migration authority. Every deployed database records exactly one supported migration lineage. Migration scripts are reviewed source files; autogenerated output is only a starting point.

## Migration rules

Every migration must:

- Have a unique revision and correct parent.
- Include purpose and operational impact.
- Be deterministic and transaction-safe where PostgreSQL permits.
- Preserve identifiers and scientific provenance.
- Avoid relying on application code that may change later.
- Include indexes, constraints, comments, and PostGIS changes explicitly.
- Be tested from an empty database and the previous production revision.
- State whether downgrade is supported.

Never modify an applied migration. Correct it with a new revision.

## Expand-and-contract workflow

For incompatible changes:

1. **Expand:** add nullable columns, new tables, or compatible indexes.
2. Deploy code able to read old and new representations.
3. Backfill in bounded, restartable batches.
4. Validate counts, checksums, and semantic equivalence.
5. Switch reads and writes to the new representation.
6. Observe for at least one normal operational cycle.
7. **Contract:** remove obsolete fields in a later release.

Application rollback must remain possible throughout the compatibility window.

## Lock and performance safety

Before production execution:

- Estimate affected rows and index size.
- Examine required table locks.
- Set appropriate lock and statement timeouts.
- Use concurrent index creation where suitable.
- Avoid large single-transaction rewrites.
- Rate-limit backfills.
- Monitor replication lag, WAL generation, connections, and latency.

## Deployment sequence

1. Confirm backup and tested recovery point.
2. Put the migration artifact under the same release identity.
3. Run preflight checks.
4. Execute backward-compatible migrations.
5. Validate the schema revision.
6. Deploy compatible application services.
7. Run database and application smoke tests.
8. Execute approved asynchronous backfills.
9. Record completion and metrics.

## Data validation

Validation includes row counts, foreign-key integrity, uniqueness, spatial validity, null rates, catalog-manifest consistency, and reference scientific queries.

## Prohibited actions

- Destructive ad hoc SQL against production.
- Automatic migration execution by every API replica.
- Renaming or dropping populated fields in the same release that changes readers.
- Rolling back a schema without determining whether newer data would be lost.
